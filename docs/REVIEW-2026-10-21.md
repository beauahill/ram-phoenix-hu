# Review of repo state (2026-10-21)

Scope: everything committed through `de50c06` (README, `docs/findings.md`,
`docs/CAMERA-MILESTONE-1.md`, and `apps/camera`). This is a desk review; no
head unit was available, and no Android SDK exists in the review environment,
so the "builds clean" claim in the last commit was not re-verified.

Verdict in one line: the reverse-engineering notes are good and mostly
consistent, but the camera app does not yet implement the one thing Milestone 1
is for (pop up on reverse from anywhere), and it has two likely show-stoppers
that will surface the first time it runs on the unit.

---

## 1. The findings: what holds up, what is stale, what is unproven

### Solid (captured live, internally consistent)
- Board/OS/panel facts (UIS7870, Android 13 userdebug `_nosec`, 1080x1920 portrait).
- The stock camera path is standard Camera2 through cameraserver, not a raw
  `/dev/video` node. This is the key insight and it changes the whole plan.
- Stock app opens Camera2 device `"14"`; `com.syu.us` opens `"10"` alongside it
  for the 360 path; physical button is owned by `com.fyt.screenbutton`.
- `/sys/lsecdcamctl/` exists, is 0666, and `fyt_car_reverse` flips 0 to 1 on
  gear R while the stock stack is running.
- Stock pain points (restart-on-error, DVR coupling, heavy GL guideline
  renderer) are real and the "reopen instead of restart" design response is right.

### Stale (earlier docs contradicted by later ones, never updated)
- `README.md` and `docs/findings.md` still say the camera is "NOT V4L2, comes
  through SYU's proprietary vendor/MCU path". The milestone doc proved it is
  plain Camera2. Either delete `findings.md` or rewrite it as a dated log.
- `README.md` architecture says "we listen to its broadcasts/intents". The
  actual mechanism found is the LSEC IPC shared `Main.DATA[]` array plus a
  sysfs node. Nothing in the code listens to a SYU broadcast.
- `README.md` stock-stack list omits `com.syu.us`, which turned out to be the
  app that owns the 360 logic, the radar UI, and the button handling.
- `findings.md` "open questions" 1 and 2 are answered in the milestone doc.

### Asserted but not backed by anything in the repo
- "3 TP2850 analog decoders (main/main2/sub video ic)" appears only in a
  comment in `HwConfig.java`. It is an important fact (it means the inputs are
  AHD/TVI analog cameras bridged to MIPI CSI-2 and explains `video_ntsc_pal`
  and `video_signal`), so it belongs in the milestone doc with how it was found.
- "Feed is plain Camera2 at 1920x1080 / 1280x720" in `HwConfig.java` is marked
  CONFIRMED but no stream size was recorded in the capture notes. The only size
  in the logs is 720x504 for the 3D-calibration path.
- "we have the exact formulas" for `com.syu.back.Module` guideline geometry.
  They are not in the repo. `GuidelineOverlay` is a hand-drawn trapezoid.
- The decompiled sources and pulled APKs live on other machines ("Crimson
  box", "gateway host") and `.gitignore` excludes `/decompiled/` and `*.apk`.
  Nobody reading this repo can re-check a single claim. Recommend committing
  the handful of decompiled classes the findings rest on (`MyCamera2`,
  `App_DoubleCamera` open/reverse paths, `ShareHandler`, `back.Module`) under
  `docs/stock-src/`, or at least the relevant excerpts.

### Inferences that need a specific test before building on them

**A. Which direction does `fyt_car_reverse` flow?**
Every other node in `/sys/lsecdcamctl/` that is 0666 (`backcar_mirror`,
`video_rotation`, `video_position`) is clearly app-to-kernel: the SYU app
writes it to configure the decoder. If `fyt_car_reverse` is the same kind of
node, it is written by `com.syu.doublecamera` or `com.syu.us` *after* they
receive reverse over the LSEC IPC. In that case it is downstream of the stock
apps, and the moment you disable them (which you must, see 2B) it will never
flip to 1 again. The capture that showed 0 to 1 was taken with the stock stack
running, so it cannot distinguish the two cases.

Test: `pm disable-user --user 0 com.syu.doublecamera com.syu.us` (and
`com.syu.video`), shift to R, `cat /sys/lsecdcamctl/fyt_car_reverse`. If it
stays 0, the real trigger is the MCU IPC (`Main.DATA[]` index / `U_BACKCAR`)
or JNI cmd 32, and `ReverseMonitor` has to be rebuilt on that.

**B. Are Camera2 ids "14" and "10" visible to a third-party app?**
On Unisoc HALs, two-digit logical ids are typically virtual multi-camera modes
and are frequently hidden from `getCameraIdList()` and gated to vendor or
platform-signed packages. The stock apps live in `/odm/app` and may be
platform-signed. The code never enumerates ids; it just calls
`openCamera("14")`. If the id is hidden this throws `IllegalArgumentException`
on every attempt and the controller loops forever at 2 s backoff.

Test, before writing more camera code:
```
adb shell dumpsys media.camera            # lists every id incl. hidden, with stream sizes
adb shell getprop | grep -i cam           # find the "CameraId6" size property
adb shell logcat -s CameraService | grep connect   # package + id on stock open
```
If 14/10 are hidden, options are: install as `priv-app` on the userdebug
build, sign with the platform key if it can be extracted, or find the vendor
whitelist property.

**C. Where does the 360 stitch actually happen?**
The doc concludes "stitching happens in the Unisoc ISP" from the log tags
`sprd_3dcalibration` and `mMultiCameraMode`. Those tags also appear on
Unisoc phones for dual-camera bokeh and are not surround-view specific. An
equally plausible reading: the truck's factory surround-view module does the
stitching and delivers a finished composite over one analog input, and device
14 is just that input in a dual-sensor wrapper. The practical conclusion
(bind the same devices, do not stitch in-app) survives either way, but the
layout assumption does not: the app assumes dev 10 is an "overhead" panel to
put at the top of the screen. Nobody has looked at what dev 10 shows. Open it
on its own and look before designing the 360 layout.

**D. "No IPC/root needed" for sysfs.**
0666 is DAC. SELinux is MAC. Reads of generic `sysfs` from `untrusted_app` are
usually allowed; writes almost never are, unless vendor policy labels these
nodes and grants a domain. Check `getenforce` and watch `dmesg | grep avc`
when the app first runs. Reads (what the app does today) are probably fine.
Writes (`Sysfs.writeInt`, currently unused) will likely need priv-app.

## 2. The camera app: functional gaps

**A. The reverse trigger only works while the app is already on screen.**
`ReverseMonitor` is started in `onResume` and stopped in `onPause`. When the
launcher or nav is in front, nothing is polling, and nothing would bring the
activity up anyway: `bringToFront()` just sets the decor view visible (a
no-op), `ReverseReceiver` only logs, and there is no service, no
`startActivity`, no `FLAG_ACTIVITY_NEW_TASK`. The commit message says
"ReverseMonitor ... + BOOT receiver" as if this works. It does not. This is
the core Milestone 1 deliverable.

What it needs: a foreground service started at boot (from `ReverseReceiver`)
and on first launch, polling the reverse flag, and launching `MainActivity`
with `NEW_TASK` on 0 to 1. Android 10+ blocks background activity starts, so
one of: `SYSTEM_ALERT_WINDOW` actually granted
(`appops set com.ramphoenix.camera SYSTEM_ALERT_WINDOW allow`), a
full-screen-intent notification, or priv-app install. On a userdebug unit
with root, priv-app is the clean answer and also solves 1B and 1D.

**B. Nothing handles reverse disengaging.** On 1 to 0 the app stays in front
showing the rear camera. The stock behaviour returns to the previous screen.
Needs `moveTaskToBack(true)` (or `finish()`) when the session was
reverse-initiated, and nothing when the user opened it manually.

**C. The stock apps are still installed and will fight for the camera.**
`com.syu.doublecamera` will still pop up on reverse and open device 14.
Camera2 arbitration evicts the lower-priority client, so our app gets
`onDisconnected` and sits in its reopen loop while the stock UI shows. The
plan needs an explicit step: disable `com.syu.doublecamera` (and decide what
to do about `com.syu.us`, which also owns the physical button and radar UI,
so disabling it may kill those).

**D. The physical button path is not hooked.** `com.syu.us` launches the
stock camera on button press; the repo does not yet know what intent or
component it uses. Decompile `com.syu.us` for that launch call. If it is an
explicit component intent it cannot be intercepted; the realistic route is
to watch the same `U_CAMERA_MODE` signal `com.syu.us` reacts to.

**E. Runtime CAMERA permission.** First launch shows a permission dialog. On
a reverse-triggered launch that blocks the feed. Pre-grant at install
(`pm grant com.ramphoenix.camera android.permission.CAMERA`) and document it.

## 3. The camera app: code defects

Ordered by how likely each is to break the first run.

1. **Stream size is never set; the session will almost certainly fail to
   configure.** `HwConfig.CAP_WIDTH/CAP_HEIGHT` are declared and never used.
   `CameraController` adds the raw `SurfaceView` surface, which is 1080x1920
   portrait. Camera2 configures the stream at the surface's size; the HAL will
   not offer 1080x1920 for an analog input, so `onConfigureFailed` fires and
   the controller loops. Fix: call `holder.setFixedSize(w, h)` with a size
   taken from `StreamConfigurationMap.getOutputSizes(SurfaceHolder.class)`
   before opening. (`CameraController.java:131`)

2. **Aspect ratio.** Even once configured, a 16:9 buffer on a match_parent
   SurfaceView in portrait is stretched to 9:16. The main surface, the aux
   surface, and `GuidelineOverlay` all need to live in a sized 16:9 box
   (1080x608 for a full-width strip), with the overlay matching the video box,
   not the screen. The stock app letterboxes; this one does not.
   (`activity_camera.xml`, `GuidelineOverlay.java`)

3. **Shared `StateCallback` lets a stale open win.** `open(id)` while a
   previous `openCamera` is in flight: `doClose` finds nothing to close, the
   old `onOpened` arrives later and overwrites `device`, then the new one does
   too. Two devices open on one surface, the first leaks. Guard with a
   per-open token or close any device whose id is not the current one in
   `onOpened`. (`CameraController.java:107`)

4. **Sensor ticker runs forever.** `startSensorTicker` posts a self-rescheduling
   runnable on a main-thread handler that is never cancelled, so it keeps the
   destroyed activity alive and invalidates a static view at 15 fps even when
   the source is the stub. Cancel it in `onDestroy`, and only tick when
   `source.available()`. (`MainActivity.java:160`)

5. **360 layout.** `surface_aux` is 720dp tall over a full-screen
   `surface_main`. 720dp means different pixel heights depending on the unit's
   density, which the repo has not recorded (`wm density`). Both panes need
   explicit, computed sizes. (`activity_camera.xml`)

6. **Manifest attribute.** `android:showOnLockScreen` is a deprecated attr
   (API 23) whose meaning is not "show when locked"; the modern one is
   `android:showWhenLocked`. The code also sets `FLAG_SHOW_WHEN_LOCKED`, so
   this is redundant rather than broken. (`AndroidManifest.xml`)

7. **Commit message overstates what is wired.** "Geometry knobs
   (mirror/rotation/position) read from sysfs": only `backcar_mirror` is read,
   and mirroring the guideline overlay has no visible effect because the
   overlay is left-right symmetric. The rotation/position/vertical/signal
   nodes are constants only.

8. **Hardcoded truck geometry is unused.** `WHEELBASE_IN`, `TRACK_WIDTH_IN`,
   `CAM_HEIGHT_IN` are referenced nowhere. Fine as placeholders, but the
   comment in `GuidelineOverlay` says geometry is "driven by HwConfig truck
   dims", which it is not.

9. **Minor.** `ReverseMonitor.lastState` is read cross-thread without
   `volatile`. `ReverseReceiver` is exported with no permission (harmless, it
   only logs). No `strings.xml`, no launcher icon, no tests, no CI. Build
   config (AGP 8.5.2 / Gradle 8.9 / JDK 17 / compile 34 / target 33) is
   internally consistent.
