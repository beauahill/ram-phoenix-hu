## The finding that changes the plan

Device 14 is **not a raw camera**. It is the composited **CVBS output of the 360 ECU**.
The ECU burns its own OSD into the video: view-select buttons (rear / overhead+rear / truck-bed),
zoom, close X, "Adjust Centerline", and its dashed centerline. Those are pixels, not Android views.

1. **Resolution ceiling is the ECU analog output (~720x480 class).** No Android-side change makes it sharper.
   Our app fixes lag, black-flash and layout, not source resolution.
2. **View switching (front / rear / 360) is a command to the ECU**, not a different Camera2 ID.
   Stock com.syu.us forwards touches on the OSD buttons to the ECU via canbus. Next RE target:
   that touch/command write path.
3. Our guidelines duplicate the ECU's own. Hide ours, or find the ECU command that disables its OSD.
4. The popup menu over the feed was com.syu.fytgesture (assistive touch), not the camera.

## Reverse trigger test (08:52, stock doublecamera + 360 disabled-state as of this session)

Two shifts into R. A 20 Hz poll of `/sys/lsecdcamctl/fyt_car_reverse` (7,154 samples over 10 min) read **0 every time**.
Meanwhile the real signal path fired cleanly both times:

| t | event |
|---|---|
| 08:52:21.597 | kernel uevent `GPIO_NAME=car-reverse GPIO_STATE=on` (i2c sensor-main2@2d), logged by tag `chip` in pid 30301 |
| 08:52:22.365 | `Signal: backcar : 1` (same pid 30301), ~770 ms after the GPIO |
| 08:52:22.618 | `com.syu.us` opens camera 10 |
| 08:52:28.197 / .200 | GPIO `over` → `backcar : 0`, cam 10 closed |
| 08:52:39.7–40.48 | second short shift, same sequence |

**Conclusion:** `fyt_car_reverse` is written by a stock camera app, not the kernel. With those apps disabled it is dead.
The `ReverseMonitor` sysfs trigger cannot work as the primary path. PhoenixCam logged nothing during the test,
confirming it never saw a transition.

**New trigger candidates, in order of preference:**
1. The LSEC IPC `U_BACKCAR` signal (the `backcar : 1` line), the same source the stock apps subscribe to. Needs the
   IPC bind path decompiled from `com.syu.us` / `doublecamera`. Fires ~770 ms after the GPIO; the GPIO itself is faster.
2. The kernel `car-reverse` GPIO uevent directly (fastest, ~0 ms). SELinux is permissive on this unit, so a
   kobject-uevent netlink listener may be reachable from our app; untested.
3. Re-enable whichever stock app writes the node and keep polling it (fallback only, reintroduces the fight for cam 14).

Also: `com.syu.us` still grabs cam 10 on reverse and draws over us. It must be disabled or out-raced once our trigger is live.
Pid 30301 needs identifying next truck session (`ps -A | grep 30301`); it is the process that owns both the GPIO observer and the backcar signal.

## Reverse trigger via IPC: PROVEN (16:01–16:02, adb pinned to tcp 5555)

Setup: camera app `d2955e0` build installed, `ReverseService` running, bound to
`com.syu.ms/app.ToolkitService`. Stock `com.syu.us`, `doublecamera`, `fourcamera2` disabled.
Beau shifted R → out, pressed driver temp +, shifted R → out again. Full logcat captured.

### Shift 1

### Shift 2
| time | event |
|---|---|
| 16:02:15.294 | GPIO → on |
| 16:02:16.496 | `backcar : 1` |
| 16:02:16.498 | `U_BACKCAR -> 1` (our app) |
| 16:02:16.577 | `Camera 14: Opened` |
| 16:02:16.629 | first 720×504 NV21 buffer allocated for our SurfaceView |
| 16:02:17.794 | `U_BACKCAR -> 0` → hide |

**Verdict:** the `MAIN/12` subscription is the correct trigger. Our end-to-end (IPC → activity →
first frame) is ~130 ms. The 1.2–1.3 s between the GPIO uevent and `backcar : 1` is entirely
inside `com.syu.ms` (`jni_exe_cmd_get_boot_reverse_status`, chip signal checks). That is the
same latency the stock camera has; we did not add any.

**The process that emits `backcar` is `com.syu.ms` (pid 30301).** It owns the GPIO uevent
handler, the TP2850 chip signal poll (`Chip6854 handleSignal`), and the ToolkitService.

`com.syu.ms` still reads/writes `/sys/lsecdcamctl/fyt_car_reverse` on every shift
(`jni_exe_cmd_get_boot_reverse_status` → OPEN OK), yet the node read 0 throughout the 08:52
poll. So it writes it only in some code path (likely the doublecamera boot-reverse handshake),
confirming the sysfs flag is not a usable trigger.

### Camera lifecycle (dumpsys media.camera)
Device 14 CONNECT/DISCONNECT pairs line up with every SHOW/HIDE; device 14 is closed with no
client after the session. No leak. One inefficiency: the HIDE intent is delivered to the
resumed activity, the surface is recreated, and cam 14 is re-opened for ~7 s until the
activity stops (16:01:59 DISCONNECT → CONNECT, 16:02:06 DISCONNECT). Fix: skip the open when a
HIDE is pending.

## Climate press (16:02:11)
Driver temp + on the stock strip (drawn by `com.fyt.screenbutton`, pid 3057) produced exactly
one canbus update: `onRefresh updateCode = 27` + `U_AIR_TEMP_LEFT isRCRQ = false`. That matches
the decoded table in `CANBUS-IPC.md` (27 = driver temp). The **send** side (button id 24/x,
press vs. release) is not visible from the receive side; only the result is. Confirming
press/release semantics needs our own app to issue `cmd(CANBUS, 0, {24, 1})` and watch for
code 27. That is a one-line debug action to add to the launcher's climate strip.
